The blueprint. The architect (`ws-architect`) writes it before any code is dispatched; the PR is judged against it.

## Scope
What this workstream builds, and what it explicitly leaves for later.

## Files
Every path in backticks, one per file or directory; `scripts/board_check.py` flags PR edits outside this list. A bare
file name right after a full path in the same bullet is read as a sibling of it. Any `tests/` directory is always
allowed.

Owned by this workstream:
- `src/<area>/` (new: what lives here)
- `docs/<area>.md`

Named edits in neighbours' code:
- `src/<neighbour>/models.py`: add `<Field>` to `<Model>`.
- `src/<neighbour>/routes.py`: the `<endpoint>` response carries `<field>`.

## Interfaces
Ports, wire messages, CLI flags and config the work adds or changes, with signatures or field names. Fix the
interfaces; leave the internals to the implementer. When another blueprint shares an interface, say which owns it.

## Contract changes
Each change `{{CONTRACTS_DIR}}` needs, as a `contract-change` issue (#) the foreman applies before dispatch, or "none".

## Exit criteria
Each one a check someone can run: a test name, or a command and its expected result.
- [ ] `tests/test_<area>.py::test_<behaviour>`: <what it shows>.
- [ ] `<command>` prints / returns <expected>.
- [ ] `python3 scripts/board_check.py` reports no file outside this Files list for the PR.

## Owner decisions
Defaults, prices, policy and anything that changes what users see, each filed as a `for-foreman` issue with a
recommendation. Mark which ones block dispatch.
- #: <question> (recommend: <answer>; blocks dispatch: yes | no)

## Verification plan
What the fakes cannot cover (live services, a real browser or device, how it looks or sounds), who checks it and how.
Say who can pay each item: the owner (eyes, ears, taste) or an agent with the right environment; an item that needs a
device but not a person goes to an agent, not to the owner's session. The implementer files each one left open as a
`needs-verification` issue with this workstream's milestone.
- <what>: <how to check it>. <owner | agent with <environment> | milestone audit | later workstream>.

## Tasks
Ordered. Step by step for `ws-mechanical` work; milestones and acceptance tests only for `ws-design` work. Each task
carries an environment tag: `[any]`, `[<machine or device>]` or `[owner-present]` (see FOREMAN.md, "Environment"). A
session without a task's environment does not start it; it names it as the next task for a session that has it.
1. `[any]` <step>. Accept: <exit criterion>.
2. `[any]` **PR.** One PR, `Closes #<issue>`; `needs-verification` issues filed and linked from "Not verified". Expected size:
   about <n> lines of code (tests and fixtures not counted; split the issue if it is over about 1,500).

## Rules
- Code against `{{CONTRACTS_DIR}}` and `{{PORTS_DIR}}`; fake your neighbours.
- Deadline, timeout and retry tests use virtual time (a fake clock or a virtual-time event loop), not wall-clock
  sleeps: wall-clock races pass locally and flake on CI.
- Generated code is regenerated by its script, never edited by hand.
- Do not edit `{{CONTRACTS_DIR}}` -- open a `contract-change` issue for the foreman.
- Stay inside the Files list above; an edit you need outside it gets a `for-foreman` issue first.
- Work in your own git worktree/branch `ws<N>/<topic>`; one PR per issue; CI must be green.
- Notes, questions and decision requests for the foreman: file an issue with the `for-foreman` label (see FOREMAN.md).
  Do not leave them only in PR comments.
