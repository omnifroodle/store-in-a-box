# foreman-template

A starter kit for running a project with a **foreman** (one session that owns the contracts, the board and reviews)
and **workstream agents** (one bounded job each, in its own worktree, one PR each). It is taken from the lcp project and
reviewed against mimics.

## What is in it
- `FOREMAN.md`: the roles, the foreman's loop (inbox, catch-up, board check, blueprint, dispatch, check, report), the
  review gate, contract changes, milestones and verification debt.
- `.claude/agents/`: four agent types with model and effort set in the frontmatter: `ws-architect` (blueprints),
  `ws-design` and `ws-mechanical` (build), `ws-reviewer` (the gate, root cause analysis, audits). The foreman picks one
  per dispatch with `subagent_type`.
- `.github/`: the "Note for the foreman" issue template (the `for-foreman` inbox) and a PR template with exit
  criteria, assumptions and a "not verified" section.
- `docs/workstreams/TEMPLATE.md`, `docs/decisions/000-template.md`: a blueprint and a decision note.
  `docs/review-log.md`: one line per gated PR.
- `scripts/board_check.py`: finds where the board has fallen behind the code (`--self-test` checks its pure helpers).
  `scripts/setup_labels.sh`: the labels the loop relies on.
- `.claude/skills/foreman-init/`: the setup skill. It asks the owner the questions that cannot be defaulted and fills in
  the placeholders (marked with double braces).

## What's new in v1
From the lcp foreman's field report in the breakroom, "lcp foreman: field report on the review gate, architect and
baseline audit, 2026-10-05" (in `concepts/foreman-pattern.md`), and the 2026-10-04 entry on usage limits and the review
gate before it.
- **Two new roles.** An architect writes a blueprint (Scope, Files, Interfaces, Contract changes, runnable Exit
  criteria, Owner decisions, Verification plan, Tasks) before any code is dispatched. A reviewer audits PRs cold.
- **A bounded review gate.** Four blocking reasons only; one fix round by the original agent; a re-check of only the
  findings; then the owner decides. Logged in `docs/review-log.md`.
- **Verification debt as issues.** Each unverified item is a `needs-verification` issue on the milestone; a milestone
  is not tagged with one open, and a milestone audit by the reviewer comes before the tag.
- **New rules from the field:** a baseline audit when adopting the gate on existing code; test two PRs that touch the
  same file merged together; a recurring follow-up sweep and owner verification session; read back spend and safety
  config from the running system; the PR size cap counts code lines only; clean up reviewer worktrees after each gate.
- **`board_check.py`** checks PR edits against the blueprint's Files list, lists `needs-verification` per milestone,
  PRs over the size cap and worktrees with no PR.

To pick these up in a project set up from v0, run `foreman-init` again (see "Upgrading" in the skill).

## What's new in v1.1
From a review of the kit by a second project's foreman with a different shape (device work, sessions spread over
several machines), plus two lessons from the v1 field report that v1 left out. The notes are in the breakroom's
`inbox/` (2026-10-05).
- **Environments per task**, not per workstream, with `owner-present` and single-instance environments (one device,
  one shared stack) and who may use them. A session never starts a task without its environment; it names it as the
  next task instead.
- **Contracts:** generated code is regenerated by script, never by hand; ask whether CI fails on stale generated
  types; operational data seeded from contract fixtures makes a live value change a contract change.
- **Inbox:** GitHub issues only. The repo-file inbox is gone; a machine without `gh` has the owner relay its note, or
  files a short-lived issue from another machine.
- **foreman-init:** a step 0 that inventories existing equivalents (briefs, ADRs, PR template, labels, ledgers) and
  maps them instead of adding parallel files; a dry-run mode; a first question round of 4, with the rest in a second
  round.
- **Merging:** the foreman never runs `gh pr merge` unless the owner asks for that PR.
- **Scheduled passes:** run once by hand first, then check the first scheduled run (an unattended run can stall on a
  permission prompt nobody sees).
- **Usage:** one user-level usage log with a project tag per snapshot, since plan usage is one pool across projects.
- **`board_check.py`** flags merged PRs with comments posted after the merge, until the foreman replies with
  `[foreman: seen]`.
- **Virtual time** for deadline and timeout tests, and **verification debt split by who can pay it** (the owner, or an
  agent with the device).

To pick these up in a project set up from v1, run `foreman-init` again, as a dry run first.

## Use it
**New project:** `gh repo create <owner>/<name> --private --template omnifroodle/foreman-template`, clone it, start Claude
Code in it, and say "set up a foreman" (or run `/foreman-init`).

**Existing project:** copy `.claude/skills/foreman-init/` into the repo and run it. It adds only what is missing and
asks before changing any file that already exists.

## How this relates to the foreman breakroom
The breakroom (an Obsidian vault on the owner's machine) is where foremen talk: the cross-project mailbox, and the
`concepts/foreman-pattern.md` page with lessons, disagreements and the reasons behind them. This repo holds only the
settled result, written as instructions.

A lesson starts in the breakroom. When the foremen agree on it, someone opens a PR here so new projects get it by
default, and runs `foreman-init` again in existing projects to pick it up. A PR here should link the breakroom entry it
comes from.
